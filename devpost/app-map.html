Multi-Timeframe Stock Screener — App Map

What this app does

A Python desktop tool that fetches real stock price data, detects candlestick patterns and indicator signals across two timeframes (daily trend + 1h entry trigger), scores each ticker by confluence, and surfaces ranked LONG and SHORT opportunities in a native desktop window — no browser required.

Data flow — one scan, end to end

Follow one action through the code

Click "Run Fresh Scan" → here's the exact path through the codebase:

1
ui/index.html — runScan()

JS disables the button, shows the spinner, calls fetch('/api/scan', {method:'POST'}). On response, calls renderTable() with the JSON result.

2
app.py — post_scan()

Flask handler reads config.json for the ticker list, calls the three screener modules in sequence, assembles and returns the JSON response.

3
screener/data_fetcher.py — fetch_daily() + fetch_1h()

Downloads OHLCV DataFrames from Yahoo Finance via yfinance.download(). Flattens the MultiIndex columns with get_level_values(0). Returns dict[ticker → DataFrame].

4
screener/pattern_detector.py — detect_patterns()

Runs 8 pattern functions on df.iloc[-1] (last complete candle). Each function checks OHLCV ratios. _candle_label() appends the candle date and a ⚠ stale flag if the data is old. Returns signal strings.

5
screener/indicator_detector.py — detect_indicators()

Uses the ta library to compute MACD(12,26,9), BB(20,2σ), and RSI(14). Checks crossover on candles [-2]→[-1] for MACD; single-candle threshold for BB and RSI. Returns signal strings with date labels.

6
screener/scorer.py — score_tickers()

Merges pattern + indicator signals per ticker. _classify() assigns +1/−1 via keyword matching. Sums to a net score, excludes zeros, sorts by magnitude → 1h volume → absolute % change → alphabetical. Returns {"long": [...], "short": [...]}.

To change this, start here

Add a new candlestick pattern

screener/pattern_detector.py — add a new _my_pattern(df) function, call it inside detect_patterns(), append the signal string. Name it so the keyword matcher in scorer.py > _BULLISH_KEYWORDS or _BEARISH_KEYWORDS will pick it up automatically.

Add a new indicator signal

screener/indicator_detector.py — add a helper function and call it from detect_indicators(). Add the keyword to scorer.py > _BULLISH_KEYWORDS or _BEARISH_KEYWORDS.

Change the default watchlist

Edit config.json directly, or use the ⚙ Watchlist editor in the running app. The app reads config.json fresh on every scan.

Add a new timeframe (e.g. weekly)

screener/data_fetcher.py — add fetch_weekly() using interval="1wk". Then call it in app.py > post_scan() alongside daily and 1h, passing "weekly" as the timeframe label to detect_patterns() and detect_indicators().

Change the dashboard look

ui/index.html — all CSS is in the inline <style> block at the top. CSS custom properties (variables) are defined under :root — change --green, --bg, --surface etc. to retheme the whole UI.

Adjust staleness thresholds

screener/pattern_detector.py > _candle_label() — change the 3 in (now - last_dt).days > 3 for daily, or the 26 in .total_seconds() > 26 * 3600 for intraday.

Decisions worth knowing

Why pywebview + Flask instead of a browser app?
The PRD required no external browser — the app should open as a native desktop window. pywebview wraps a system WebKit view (Safari engine on macOS) and renders the HTML/CSS frontend inside it. Flask runs on a background daemon thread on localhost:5000. The frontend makes standard fetch() calls to it — exactly like a normal web page, except both are on your machine. This means the frontend is debuggable in a real browser during development.
Why keyword matching in the scorer instead of signal type enums?
Signal strings carry their classification in their name by design — "Bullish Engulfing", "MACD bearish crossover". Keyword matching means adding a new detector signal automatically flows through to scoring as long as the string follows the naming convention. No separate registry or enum to update. The tradeoff: a typo in a signal name produces a score of 0 silently. For a PoC this is acceptable; a production version would use typed signal objects.
Why is pandas-ta not used despite being in the original spec?
pandas-ta has no published PyPI release compatible with Python 3.10+. Discovered during environment setup. Replaced with ta==0.11.0 which covers MACD, Bollinger Bands, and RSI with a clean pandas API. Candlestick patterns use manual OHLCV math throughout — which was already the specced fallback approach.
Why does yfinance return a MultiIndex and how do we handle it?
yfinance.download() always returns a MultiIndex column structure (field, ticker) — e.g. ('Close', 'AAPL') — even when downloading a single ticker. data_fetcher.py > _normalise() flattens it with df.columns.get_level_values(0) so all downstream code receives a simple [Open, High, Low, Close, Volume] DataFrame. This is a consistent yfinance 1.x behaviour worth knowing for any project using the library.

A practice to reuse

Specify the response shape before writing the handler

In spec.md > POST /api/scan, the JSON response shape was written out explicitly before any code existed:

{"long": [{"ticker": str, "score": int, "signals": [str]}], "short": [...], "timestamp": str}

Because that contract existed in the spec, the Flask handler, the scorer's return type, and the JS renderTable() function were all written independently and wired together without a single shape mismatch. The one place the build needed a revision (pandas-ta unavailability) was a dependency that wasn't verified in the spec before writing it.

Reuse this on your next project: before writing any API handler, write the exact JSON response shape in the spec. Run pip index versions <library> before adding any dependency to the stack. These two habits eliminate the most common sources of agent build friction.

How to run the app

source venv/bin/activate && python main.py

Requires Python 3.10+. Install dependencies with pip install -r requirements.txt inside the venv. No browser needed — a native desktop window opens automatically.
